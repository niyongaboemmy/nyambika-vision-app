# ADR-0005: Agentic commerce and Try-on as a Service

- Status: Accepted (R3, E36/E37)

## Context
FR-AGT-01..06/08 ask for a public catalogue, agent protocols (UCP/ACP, MCP), explicit user confirmation before any agent-initiated payment, member opt-in/out, and a B2B try-on API. The product principles still bind: shoppers buy from the maker's page and pay the maker directly (OP-2/3), and shoppers' twins never leave Nyambika (OP-5).

## Decision
- **One module** (`apps/api/src/modules/agents`) owns every external surface. All routes are `@Public()` for the user `AuthGuard` and go through `AgentGuard`: kill switch (`agents.kill_switch` / `partners.kill_switch` flags) → key → scopes/kind → per-IP and per-key fixed-window rate limits (Redis, memory fallback) → monthly per-key quota → `AgentCall` audit row (IP stored as a hash only).
- **API keys:** `nya_live_…` / `nya_test_…` (≈190 bits). Only `HMAC-SHA256(pepper=JWT_SECRET, secret)` is stored; the 16-char prefix identifies a key. Shown once on creation. Scopes: `catalogue:read`, `checkout:write`, `mcp:use`, `tryon:write`, `usage:read`. Client kinds AGENT/PARTNER gate which routes a key can reach.
- **Public catalogue** `/v1/public/*`: only PUBLISHED products of PUBLISHED, **verified** pages not opted out (`AgentChannelSetting`, no row = opted in). Opaque id cursors, weak ETags/304, coarse availability (`in_stock|low_stock|out_of_stock|made_to_order`), schema.org Product + one Offer per variant (also via `Accept: application/ld+json`). Search reuses the Muse `rank()` (relevance, then fair rotation across makers). OpenAPI 3.1 is generated from the Zod response schemas with `z.toJSONSchema` (the contract tests parse real responses with the same schemas) and served at `/v1/public/openapi.json`.
- **Checkout = cart mandate, never delegated payment.** An agent creates a session for **one maker payout account**; Nyambika snapshots the cart and signs `{session, nonce, page, total, sha256(items), exp}` (HMAC-SHA256, 30 min). The link `/confirm/<token>` shows maker, items, price, who asked and "paid directly to"; the signed-in shopper confirms with the hold gesture. Confirmation atomically consumes the mandate (`updateMany … mandateUsedAt IS NULL AND exp > now`), re-checks live prices (refuses if the cart changed), reserves stock and creates the normal order + Mobile Money request to the maker. Session status is derived from the order, so the agent can poll it but never sees shopper data.
- **MCP:** official `@modelcontextprotocol/sdk` 1.32.2 (protocol `2025-11-25`), Streamable HTTP at `POST /mcp`, **stateless** (one server per request, JSON responses), bound to the caller's key. Tools: `search_products`, `get_product`, `get_maker`, `check_availability`, `create_checkout_intent`; resource `nyambika://catalogue`.
- **Try-on as a Service:** `POST /v1/partner/tryon` takes a garment image + one of five **synthetic** models (`nya-model-1..5`, the studio personas). BullMQ queue `partner-tryon`: garment assess → `/v1/tryon` (HD) → guard → C2PA → sandbox watermark → metering. Admission per contract (`admit()`): live needs an ACTIVE contract in its window; included up to `monthlyQuota`, then `overagePriceRwf` or refusal with `hardCap`; sandbox keys work on DRAFT contracts with a daily cap, are watermarked and never billed. Withheld/failed jobs are never billed. Results are 5-minute HMAC-signed links. Webhooks: `Nyambika-Signature: t=<unix>,v1=HMAC-SHA256(secret, "t.body")`, 6 attempts with exponential backoff; secret sealed with AES-256-GCM, shown once.

## Protocol alignment (honest)
- **ACP** (OpenAI/Stripe): path and object shape of `checkout_sessions` (create / get / complete / cancel, `line_items[].item {id, quantity}`, `totals[]`, `messages[]`, `links[]`, `Idempotency-Key`, `API-Version` header set to `2025-09-29`). That version string is from memory and was not re-verified against the current spec. Not implemented: update (`POST /checkout_sessions/{id}`), request signing (`Signature`/`Timestamp`), delegated payment tokens (by design `complete` always answers 409 `REQUIRES_USER_CONFIRMATION`), buyer/fulfilment address fields (the shopper enters them in Nyambika).
- **UCP** (Google/Shopify): `/.well-known/ucp` business profile in the shape documented for version `2026-08-25` (`ucp.version`, `services["dev.ucp.shopping"]` with REST and MCP transports, `capabilities["dev.ucp.shopping.checkout"]`, empty `payment_handlers`, empty `keys`), plus `/ucp/v1/checkout-sessions` create/get/cancel with UCP status words (`incomplete` + `continue_url` = the mandate link, `complete_in_progress`, `completed`, `canceled`). Not implemented: `UCP-Agent` profile negotiation, `PUT` update, request signing / JWK keys, payment handlers, `complete`.
- **AP2:** only the idea of a merchant-signed cart mandate confirmed by the user; no AP2 verifiable-credential format.

## Consequences
- Agents can discover and prepare orders, but money only moves after the shopper's PIN, straight to the maker.
- Partner API never touches personal data; FR-AGT-06's "partner sends a person image" is deliberately not offered until a partner-side consent and DPA model exists.
- SRS FR-AGT-08 (webhooks to members' own systems for orders/stock) is not built here; the task brief mapped FR-AGT-08 to agent identity & safety.
